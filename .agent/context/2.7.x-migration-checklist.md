# 2.7.x backport 降级适配指南

> 从 master 分支 cherry-pick 代码到 2.7.x 分支时，需要做以下降级适配。
> 2.7.x = Spring Boot 2.7.x + javax + Java 8
>
> **本指南是 master → 2.7.x 同步的唯一指导文件。** 每次同步的阅读顺序：
> **第 13 章（判范围）→ 第 14 章（做审计）→ 第 15 章（版本层速查）→ 第 12 章（逐类别适配操作）→ 第 16 章（本地验收）→ 第 17 章（文档留痕）**。
> 第 1–11 章是各类别降级适配的对照表；证据与逐轮审计记录归档在 `docs/feature/2.7.x-sync-gap-checklist.md`（本地归档、不入库），本指南只保留**可复用**的口径与结论。

---

## 0. 通用原则

### 0.1 不需要 backport 的文件

以下 master-only 文件在 cherry-pick 时**直接跳过**，不进入 2.7.x：

- `WebHttpHeaders.java` — 基于 Spring 6 `HttpHeaders` 的增强子类（Content-Type 缓存 + Netty 常量名直通）。2.7.x 用原生 `HttpHeaders` 即可
- `native-image/` 目录下的所有文件 — GraalVM 配置
- `VirtualThreadE2ETest.java` — 虚拟线程测试（需要 JDK 21+）
- `GraalVmNativeImageConfigTest.java` — GraalVM 配置验证

**如果 cherry-pick 引入了对这些文件的引用，需要适配兼容代码**（见各章节说明）。

### 0.2 通用操作逻辑

```
master 代码                                      2.7.x 代码
──────────────────────────────────────────────  ──────────────────────────────
jakarta.servlet.*                          →    javax.servlet.*
jakarta.validation.*                       →    javax.validation.*
jakarta.annotation.*                       →    javax.annotation.*
HttpMethod.valueOf()                       →    HttpMethod.resolve()
Set<HttpMethod>                            →    EnumSet<HttpMethod>
HashSet<>(...) (for HttpMethod)            →    EnumSet.copyOf(...)
HttpMethod.toString()                      →    HttpMethod.name()
getMethod() (代替 getBridgedMethod())       →    getBridgedMethod()（看情况）
HttpStatusCode                             →    HttpStatus
```

## 1. POM

### 1.1 Spring Boot 版本管理方式
```
master:  <dependencyManagement> import spring-boot-dependencies 3.5.16
2.7.x:   <dependencyManagement> import spring-boot-dependencies 2.7.18
```
两个分支的根 pom **都没有 `<parent>`**——是独立 POM（自己的 groupId/version），
仅通过 `dependencyManagement` 里 `import` 的 `spring-boot-dependencies` BOM 取得
Spring Boot 及其整套依赖的版本管理。因此同步时不存在「改 parent version」这一步。

### 1.2 Java 版本
```
master:  <java.version>17</java.version>
2.7.x:   <java.version>8</java.version>
```

### 1.3 项目版本
```
master:  <version>3.5.x</version>
2.7.x:   <version>2.7.x</version>
```

### 1.4 依赖回退

| master | 2.7.x | 原因 |
|--------|-------|------|
| jakarta.servlet-api 6.0.0 → **移除** | 改为 **javax.servlet-api**（显式管理版本） | jakarta → javax 回退 |
| spring-boot-admin-client 3.2.0 | → `2.7.10` | SB 2.7 匹配版本 |
| springdoc-openapi-starter-common:2.3.0 | → `springdoc-openapi-common:1.7.0` | GroupId 从 `org.springdoc.openapi` → `org.springdoc` |
| 由 SB3 parent 管理的版本移除了显式声明 | **恢复显式版本声明**（lombok, jupiter, mockito, byte-buddy, assertj 等） | SB 2.7 parent 可能未管理或版本不同 |

> **注意**：springdoc 的 GroupId 变更（`org.springdoc.openapi` → `org.springdoc`）和 ArtifactId 变更（`springdoc-openapi-starter-common` → `springdoc-openapi-common`）容易遗漏。如果 cherry-pick 涉及 OpenAPI 相关内容，务必检查。

### 1.5 检查清单
- [ ] Parent POM 版本回退到 `2.7.18`
- [ ] Java 版本改为 `8`
- [ ] 项目版本号改为 `2.7.x`
- [ ] jakarta.servlet-api 依赖移除，改为 javax.servlet-api（显式管理版本）
- [ ] spring-boot-admin-client 版本回退到 `2.7.10`
- [ ] springdoc-openapi 改为 `springdoc-openapi-common:1.7.0`（注意 GroupId）
- [ ] 恢复已在 master 中移除但 SB2.7 parent 未管理的依赖版本声明（lombok, jupiter, mockito, byte-buddy, assertj 等）
- [ ] 检查其他第三方依赖是否需要回退版本

## 4. Spring Framework API 降级

### 4.1 HttpMethod：Interface → Enum

| master | 2.7.x |
|--------|-------|
| `HttpMethod.valueOf(String)` → 回退为 `HttpMethod.resolve(String)` | `MappingRegistry.java` 中调用点 |
| `Set<HttpMethod>` → 回退为 `EnumSet<HttpMethod>` | `HttpMethodMatcher.java`、`HttpBodyCodecRegistry.java` |
| `new HashSet<>(...)` → 回退为 `EnumSet.copyOf(...)` | `MappingRegistry.java` 中创建集合 |
| `HttpMethod.toString()` → 回退为 `HttpMethod.name()` | `HttpMethodMatcher.java` |
| `if-else` 链 → 回退为 `switch(httpMethod)` | `OpenApiAdapter.java` |

### 4.2 getMethod() → getBridgedMethod()

Spring 6 移除了 `getBridgedMethod()`，master 统一使用 `getMethod()`。2.7.x 需要改回。

| 文件 | 修改 |
|------|------|
| `InvokableHandlerMethod.java` | 恢复 `getBridgedMethod()` 覆盖方法 |
| `MappingRegistry.java` | `getMethod()` → `mappingContext.getBridgedMethod()` |
| `ReturnValueResolverRegistry.java` | 恢复 `getBridgedMethod()` |
| `SpringHandlerMethodReturnValueHandlerAdapter.java` | 恢复 `getBridgedMethod()` |
| `OpenApiAdapter.java` | `ctx.getMethod()` → `getBridgedMethod()` |

### 4.3 HttpStatusCode → HttpStatus

| 文件 | 修改 |
|------|------|
| `BaseWebServerHttpResponse.java` | `setStatusCode(HttpStatusCode)` → `setStatusCode(HttpStatus)` |
| `ResponseStatusExceptionResolver.java` | `HttpStatus.resolve(ex.getStatusCode().value())` → `ex.getStatus()` |
| `InvokableHandlerMethod.java` | `getResponseStatus()` 返回 `HttpStatus` 而非 `HttpStatusCode` |

### 4.4 检查清单
- [ ] 全局搜索 `HttpMethod.valueOf(` → 改为 `HttpMethod.resolve(`
- [ ] 全局搜索 `Set<HttpMethod>` → 改为 `EnumSet<HttpMethod>`（确认使用时需要 EnumSet 语义）
- [ ] 全局搜索 `HashSet` 涉及 HttpMethod 的 → 改为 `EnumSet.copyOf`
- [ ] 全局搜索 `.toString()` 涉及 HttpMethod 的 → 评估改为 `.name()`
- [ ] 全局搜索 `if-else` 涉及 HttpMethod 的 → 评估改回 `switch`
- [ ] 全局搜索 `getMethod()` → 评估是否需要改回 `getBridgedMethod()`
- [ ] 恢复 `getBridgedMethod` 的覆盖声明（`InvokableHandlerMethod.java`）
- [ ] 全局搜索 `HttpStatusCode` → 改为 `HttpStatus`
- [ ] 全局搜索 `.getStatusCode()` 在 `ResponseStatusException` 上的调用 → 改回 `.getStatus()`

## 5. AutoConfiguration 回退

### 5.1 spring.factories 恢复

Spring Boot 3.x 使用 `AutoConfiguration.imports`，2.7.x 仍使用 `spring.factories` 的 `EnableAutoConfiguration` 配置。

**操作**：
- 将 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 中的内容**移回** `META-INF/spring.factories` 的 `EnableAutoConfiguration` 条目中
- **删除** `AutoConfiguration.imports` 文件

### 5.2 影响模块

- `spring-boot-starter-web` — AutoConfiguration 类从 `.imports` 移回 `spring.factories`
- `spring-web-websocket` — 同样处理

### 5.3 检查清单
- [ ] 读取 `AutoConfiguration.imports` → 将条目追加到 `spring.factories` 的 `EnableAutoConfiguration` 下
- [ ] 删除 `AutoConfiguration.imports` 文件
- [ ] 保留 `spring.factories` 非 auto-configuration 的条目不变

## 10. 兼容层说明（master 已无 SB 4.x 兼容层）

自 4.1.x 分支拆出后，**master 只维护 3.5.x，不再包含任何 Spring Boot 4 / Spring 7 兼容代码**。
因此从 master backport 到 2.7.x 时，**不再需要剔除 SB 4.x 兼容层**（本章旧版列出的
`MediaTypeUtils` / `ResponseStatusExceptionAdapter` 等文件已从 master 删除）。

仅需注意：`spring-web` 内的版本适配代码（若有）应保留在 4.1.x 分支，不应出现在 master。

### 10.1 WebHttpHeaders 的处理

`WebHttpHeaders` 在 master 上是**基于 Spring 6 `HttpHeaders` 的增强子类**（Content-Type 缓存 +
Netty 常量名直通），不含任何版本兼容分支。2.7.x 下可直接跳过它、改用原生 `HttpHeaders`：

| master | 2.7.x |
|--------|-------|
| `new WebHttpHeaders()` | `new HttpHeaders()` |

### 10.2 检查清单
- [ ] cherry-pick 是否引入了 `WebHttpHeaders`？→ 改为 `HttpHeaders`（或按 10.1 处理）
- [ ] cherry-pick 是否引入了 Spring Boot 4 专属文件？→ **不应该有**（master 已清理）

## 11. spring-web-view 视图渲染模块 backport

`spring-web-view` 为新模块，backport 涉及 POM、AutoConfiguration 注册、模板引擎 API 三处差异。**最大风险是 Thymeleaf 3.0（SB 2.7）与 3.1（SB 3.2）的 `IWebContext` API 不兼容**。

### 11.1 POM 变更

- parent `pom.xml`：modules 加 `<module>spring-web-view</module>`，dependencyManagement 加 `spring-web-view`
- `spring-boot-starter-web/pom.xml`：加 `spring-web-view`（`provided`）
- `spring-web-test/pom.xml`：加 `spring-web-view`、`spring-web-mvc-support`、`thymeleaf`、`jakarta.servlet-api`→`javax.servlet-api`

### 11.2 Thymeleaf 3.0 vs 3.1 API（核心差异）

| master（Thymeleaf 3.1.2） | 2.7.x（Thymeleaf 3.0.15） |
|---------------------------|---------------------------|
| `IWebContext.getExchange()` → `IWebExchange`（瘦接口） | 无 `IWebExchange`，`IWebContext` 直接有 `getRequest()` / `getResponse()` / `getSession()` / `getServletContext()`（返回 `IThymeleafRequest` 等） |
| `ClassLoaderTemplateResolver` + `setTemplateMode(TemplateMode.HTML)` | `ClassLoaderTemplateResolver` 存在；`TemplateMode.HTML` 在 3.0 为 `SHORTEN_UNIFIED` 演变，需确认 |
| `engine.process(viewName, IContext, Writer)` | 同（3.0 存在） |

**适配**：2.7.x 的 `ThymeleafWebContext` 需改为实现 3.0 版 `IWebContext` 接口（`getRequest`/`getResponse`/`getSession`/`getServletContext`），URL 方言 `@{...}` 由 `StandardLinkBuilder` 直接读取 `getRequest().getApplicationPath()` 等，而非 `transformURL`。实现类可参照 `org.thymeleaf.context.WebContext`（3.0 servlet 版）的结构去 servlet 化。

### 11.3 Spring Framework API 降级

| 文件 | 修改 |
|------|------|
| `ModelContext.java`（原 `ModelSupport.java`） | **无需修改**——Spring 5.3 的 `ModelMap implements Model`，`ExtendedModelMap` 兼容性不变 |
| `ModelArgumentResolverProvider.java` | 无需修改 |
| `ThymeleafWebContext.java` | 重写为 3.0 `IWebContext` API（见 11.2） |
| `RedirectView.java` | 无需修改 |

### 11.4 AutoConfiguration 注册

`SpringWebViewAutoConfiguration` 类本身无需改动，但注册方式从 `AutoConfiguration.imports` 移入 `spring.factories`（见第 5 章）。

### 11.5 检查清单
- [ ] query `ThymeleafWebContext` 是否实现 3.0 版 `IWebContext`（`getRequest/getResponse/getSession/getServletContext`）
- [ ] `IWebExchange` / `IWebRequest` / `IWebApplication` 引用是否已清除（3.0 无此类型）
- [ ] 确认 `TemplateMode` 枚举与 `ClassLoaderTemplateResolver` 方法签名兼容
- [ ] `spring-web-view` 加入 parent modules + dependencyManagement
- [ ] `spring-boot-starter-web` / `spring-web-test` POM 依赖更新
- [ ] `SpringWebViewAutoConfiguration` 注册进 `spring.factories`
- [ ] `spring-web-test` 的 `jakarta.servlet-api` → `javax.servlet-api`
- [ ] `ViewRenderTest` 中 `@SpringBootTest(webEnvironment=...)` 的 SB 2.7 兼容性

## 12. Backport 操作流程

每次从 master cherry-pick 代码到 2.7.x 时，按以下顺序执行：

```
□ 0. 确认需要 backport 的 commit 范围               → 判范围见第 13 章（默认全同步 / 不做清单）
□ 1. 识别本次涉及了哪些变更类别（影响下面需要检查的章节）
     - POM 变更？               → 第 1 章
     - 包路径变更？             → 第 2 章
     - Servlet API 变更？       → 第 3 章
     - Spring API 变更？        → 第 4 章
     - AutoConfiguration 变更？ → 第 5 章
     - GraalVM 相关？           → 第 6 章（跳过）
     - 虚拟线程相关？           → 第 7 章（跳过/注意）
     - Springdoc 变更？         → 第 8 章
     - 测试代码变更？           → 第 9 章
     - SB 4.x 兼容层？          → 第 10 章（跳过+替换引用）
□ 2. 执行 cherry-pick，解决 Git 冲突
□ 3. 按识别出的类别逐项执行降级适配
□ 4. 全局扫描确认无 jakarta.* 残留                     → 第 2 章
□ 5. 全局扫描确认无 JDK 9+ API 残留                      → 第 15.1 节
□ 6. 全局扫描确认无 master-only 文件/引用残留            → 第 0.1 / 13.2 节
□ 7. 用 JDK 8 编译（不是 JDK 17）                        → 第 16 章
□ 8. 运行单元测试（单模块必须加 -am）                    → 第 16.1 节
□ 9. 运行集成测试 + 文档/门禁校验                        → 第 16.1 节
□ 10. 回查文档过期表述（同步落地后必做）并提交           → 第 17.3 节
```

## 13. 同步范围判定：默认全同步 + 不做清单

### 13.1 判定原则（勿以「API 不存在」为由跳过）

- **默认所有改动点都应同步**；「同步」= **适配式同步**：用本分支可用的机制（自有抽象 / 等价 API / 静态资源 / javax 版写法）实现**等价行为**，不是逐字照搬。
- **API 在目标版本不存在，只说明要换写法，不是跳过理由**（写法见第 4、11、15 章）。
- 只有「**连等价机制都不存在**」才归入不做，且必须给出**基于实测的硬证据**（如插件在 JDK 8 上不可用、依赖 master 独有模块）。
- 每一项「不做」都要写清：**理由 + 是否已用等价物覆盖**。

### 13.2 不做清单（版本边界 / 工具链，勿再列入待办或重报）

| 类别 | 范围 | 理由 |
|---|---|---|

### 13.3 已改判为「同步」的门禁 / CI（2026-10-12；原「门禁一律不同步」作废）

- **已同步**：`mvnw` / `mvnw.cmd` / `.mvn/wrapper/*`；根 pom 的 `maven-enforcer-plugin`（**只取 `requirePluginVersions` 一条**；`requireJavaVersion [17,)`、`enforceBytecodeVersion 17`、`requireMavenVersion` 与 JDK 8 目标冲突，**不移植**）；`ci.yml` 的 `build` / `docs` / `javadoc` 三 job；`codeql.yml`；`.github/dependabot.yml`（与 action SHA pin **成对**）；`coverage-aggregate` 模块 + 根 pom `<module>`。

### 13.4 本分支领先 master（同步时勿删 / 勿回退）

归一化复比里表现为「仅 2.7.x 有」，**不是缺口**：

- `SpringWebAutoConfiguration`：多 `WebServerInitializedEvent` 发布器（master 的 `WebServerInitializedEventAutoConfiguration` 在本分支已内联）
- `ThymeleafViewResolver`：多 native / 无 servlet 回退分支
- `BaseWebServerHttpResponse`：`setRequestAcceptHeader` / `acceptHeader`
- `AcceptLanguageLocaleCache`：有界（超限整体清空），master 为无界 `ConcurrentHashMap` —— 本分支更好
- `HttpMethodMatcher` / `MappingRegistry`：用 `EnumSet`
- `DispatcherHandler.finalizeEarlyReturn`：流式感知的早期收尾
- 配置键：`server.http.max-header-size`（+`HTTP_MAX_HEADER_SIZE`）、`server.async.timeout`（+`ASYNC_TIMEOUT`）、`server.virtual-host`
- `Http2ChannelInitializer` 的 11 参便利重载（master 收敛为 15 参）

> **唯一需要重新评估的情形**：master 的**死代码被本分支领先机制激活**而变有害。例：master 某处 `release()` 兜底在本分支因 `registerPipeliningCompletion` 而可达 ⇒ 照搬会双重释放。⇒ 同步前对这类改动做一次**可达性判定**（master 有无调用者 / 本分支是否新增了触发路径）。

## 14. 同步审计方法（判断「还差什么」）

### 14.1 三层叠加口径（互不替代）

1. **差集层**：`master` tracked 全集 vs 本地 index 全集 → 仅 master 有 / 仅本地有 / 两侧都有；对「仅 master 有」再查**磁盘是否存在**（抓静默漏提交）。
2. **内容层**：逐文件归一化后比对；余下差异按「javax 互换 / 注释 / 空白」自动放行，其余进人工定性。
3. **符号层（java 专用）**：剥离注释与字符串后提取**类型 / 方法（名 + 参数个数）/ 字段**集合，找「master 有、本地缺」的成员 —— 这是唯一能抓住「类还在但方法被漏掉」的手段。

> **基线必须用本地 `master`**，不要用 `origin/master`：本地 master 可能领先一笔未 push，会把已同步项误判成「下游反向分叉」。

### 14.2 关键步骤：token 归一化

```bash
git worktree add --detach .master-ref master                              # 1) 参考树
git diff --name-status master -- "*/src/main/java/*" "*/src/test/java/*"  # 2) 文件级差集
# 3) 归一化后做整文件 token 流比较：去注释 + 去 import + jakarta.*→javax.*
#    + HttpStatusCode.→HttpStatus. + 去掉全部空白换行
```

**为什么必须归一化**：直接看文本 diff 会把缺口**高估约 4 倍**（首轮实测 1069 个差异文件里 681 个 token 流完全一致；2.7.x 侧代码大量被压成单行、注释改写，`PerfHttpServletRequestTest` 显示 329 行「差异」实际为 0）。

### 14.3 方法学教训（4 条，均为实测踩过）

1. **不要用「两级正则替换」去注释**：块注释必须与字符串 / 行注释在**同一遍扫描**里竞争。`/**`（出现在 `// … /api/**` 注释里）会**吞代码 → 假缺口**；`//`（出现在 URL 字符串里）会**截行 → 假相等**。两者方向相反，都会让「归一化差异数」失真。
2. **「master 有方法、本地没有」≠ 缺口**，判定顺序：① 该方法在 master 全仓是否有调用者；② 本地是否已有等价机制；③ 再谈补不补。
3. **判缺口要落到「资源 / 行为」**：真正到资源泄漏级别的极少（如池化 ByteBuf 未 `release`），且能用 master 既有注释直接举证 —— 比按差异行数排序可靠。
4. 工具要用**符号计数交叉校验**兜底：同一方法在两侧的存在性与调用次数是**位置无关**的量，能立刻区分「真缺失」与「对齐假象」。

### 14.4 「缺失标识符」是唯一硬信号

收口判据：**master 有、本地没有的标识符**（类型 / 方法 / 字段 / 常量名只在 master 侧出现；折行、重排、注释噪声天然不参与）。实测 170 个「按签名判差异」的文件中，83 个**无任何缺失标识符**，余下 87 个共 686 个标识符**全部落在已知类别**（版本层 / 版本边界 / 已登记等价 / 测试基建）⇒ 无真实缺口。

### 14.5 常见假阳性（误报形态，报缺口前先排除）

- 类 / 方法**已存在**，缺的是**调用点**（`markStreamCompleted`、`addConnectionCloseHandler`、`releaseRequestOnce`、`getExpressions`）
- 缺的是**另一处**（`ParameterLimitExceededException` 已存在，缺的是请求侧 `enforceParameterLimit`；`cleanPathForOpenApi` 两侧都有）
- 两侧都有、差异在**内部逻辑**（`getRuntimeInterceptors` 的 404/405 path 过滤）
- 已按**版本边界**裁定不做，却被报成缺口（`IN_NATIVE_IMAGE` 守卫）

### 14.6 静默漏提交扫描（必做）

对 master 的 tracked 文件逐个查「**工作区存在但本地索引缺**」：被 `*.py` / `*.txt` 之类忽略规则吃掉的文件不会出现在 `git status` 里，但**别的 E2E 依赖它们 ⇒ 全新 clone 必红**（本机门禁绿只因工作区恰好有）。实测命中 7 个（4 个 `spring-web-benchmark/perf/*.py` + 3 个 E2E 测试资源），处置为 `git add -f`。

**配套**：`.gitignore` 白名单与脚本 / 资源同批同步（`!/scripts/*.py`、`!/spring-web-benchmark/perf/*.py`）。

### 14.7 编码损坏（乱码）检测

- **口径**：把文本按 **GBK 编回**、再用**严格 UTF-8**（`throwOnInvalidBytes=true`）解码，能还原中文即证明是「UTF-8 被按 GBK 读入后又存成 UTF-8」的双重编码；另用 `銆|锛|鐨`（`。`/`，`/`的` 的乱码形态）兜底扫描。
- **修复**：**只接受双向校验通过的整行回转**；含不可逆 `?` 的行手工重建。曾用「ASCII 骨架匹配 master 同行」做兜底 ⇒ **误替换 2 处语义相反的注释**，已整批回退。
- **注意**：master 侧也可能带同样乱码（`.master-ref` 工作树干净 ⇒ 已提交进 master），本分支修好后归一化复比会显示 DIFFER，**勿当缺口**。
- **Windows**：`powershell -File` 读 `.ps1` 默认按 ANSI(GBK) ⇒ 脚本内的中文字面量必须存成 **UTF-8 with BOM**。

### 14.8 结论置信度标注（写审计结论时统一使用）

| 标记 | 含义 |
|---|---|
| ✅ | 本机实测（`git grep` / `git diff` / 真跑过命令） |
| ○ | 双侧逐行实读（未跑 shell） |
| △ | 声明级粗判，**排期前需二次确认** |

## 16. 本地验收与门禁（JDK 8 口径）

### 16.1 环境与命令

- 必须**真用 JDK 8** 编译 + 运行（本机示例 `D:\soft_space\Java\jdk8u502-b07`）：`source/target=8` **不拦 JDK 9+ API**，编译通过 ≠ 能跑。
- **Windows 必须用 `.\mvnw.cmd`**（`./mvnw` 是 Linux / CI 写法）。

| 目的 | 命令 |
|---|---|
| 全量门禁 | `.\mvnw.cmd -o -B clean test` → 25 模块 SUCCESS |
| javadoc 门禁 | 先 `.\mvnw.cmd -o -B install -DskipTests -Dmaven.javadoc.skip=true -Dmaven.source.skip=true -q`，再 `.\mvnw.cmd -o -B javadoc:javadoc -Ddoclint=all,-missing` |
| 文档门禁 | `python scripts/check-docs.py`、`python scripts/check-doc-symbols.py`（`check-docs.sh` 只是调度壳，Windows 上直跑这两条即等价） |
| 泄漏门禁 | `powershell -File scripts/check-netty-leaks.ps1 -Paths <log>` |
| wrapper 自检 | `.\mvnw.cmd -v`（首次需网络下载 Maven 3.9.9） |

- **单模块测试必须带 `-am`**：`mvn -o -pl <module> test` 会用本地仓库的**旧产物**解析依赖 ⇒ 报一批假「找不到符号」；正确写法 `mvn -o -pl <module> -am test -DfailIfNoTests=false`。
- 插件类门禁（spotbugs / modernizer / japicmp / format）**本分支跑不了** ⇒ 不得以「CI 绿」替代本地验收。

### 16.2 javadoc 的 JDK 8 差异（doclint）

1. **分组语义不同**：「`@param`/`@return` 没有说明」在 JDK 8 属 **syntax** 组（warning，不判红）、JDK 9+ 才归 **missing** 组 ⇒ master 用 JDK 17 跑 `-Xdoclint:all,-missing` 是绿的，本分支用同一参数会报。**这类条目同步文本无用**（文本与 master 逐字相同），靠「只 warning」放行。
2. **模块级 `<doclint>` 覆盖 `-Ddoclint`**：`spring-web-mvc-support/pom.xml` 的 `<doclint>all,-missing,-reference</doclint>`（Spring API 镜像模块，`{@link}` 指向不在 classpath 的框架内部类）优先级更高 ⇒ 收紧 / 降级都不能只靠命令行开关统一。
3. **注释级 javadoc 修正在「剥注释」的审计里隐身** ⇒ 这是**独立可同步**的缺口类型（master 用 `{@code}` 包裹裸露的 `<` / `>` / `@`）。
4. **裸 `<` / `>` / `&` 一律被 html 组判错**：`<=0`、`->`、`=>`、`&data=`。解法：改中文措辞（「小于等于 0」）或实体化（`&gt;`、`&amp;`）；**`{@code}` 内不能用实体**（会被当字面量渲染）。
5. **`{@code}` 内行首 `@` 会被当块标签**：`<pre>{@code` 换行后紧跟 `@Configuration` ⇒ `unterminated inline tag` + `unknown tag`。解法：把注解挪到与 `{@code` **同一行**（渲染一致）；仅缩进一个空格**无效**。
6. **必须保留的刻意文本差异**（master 靠 JDK 17 放宽检查才绿，勿「修回」）：`ModelAndView.java`、`WebUtils.java`、`Jdk8GcLogParser.java` 的 `->` / `=>` 实体化，`WebSocketConfigurer.java` 的 `<pre>{@code @Configuration`。

### 16.3 计数与日志口径（避免误判）

- doclint 缺陷计数用 **distinct `file:line`**：Maven 会折行 + 重复列举，原始行数会翻倍（同一日志 152 行 vs distinct 74）。
- 日志读取加 `-J-Dfile.encoding=UTF-8`，否则 PowerShell 写出的日志丢中文消息。
- 结论要能用**同一条命令**复现；不同命令（`-Ddoclint` vs `-DadditionalJOption`）得到的数字差异，先辨析再引用。

## 17. 文档与留痕口径

### 17.1 文档同步的落点

**= 跨分支介绍性内容齐全 + 本分支事实正确**，不是把 master 的能力 / 工具链段落照搬：

- 介绍兄弟分支的内容（`4.1.x-adaptation-checklist.md`、`docs/(en/)compatibility.md` 的 master 小节）**保留**；
- 本分支**没有的能力 / 工具链**段落（Spring AI、AOT/native、虚拟线程、SpotBugs/japicmp/mvnw 章节），按本分支口径写（删除或改等价机制），**不因「对称」恢复 master 原文**；
- 只改「对本分支**事实错误**」的表述（`jakarta`→`javax`、模块数 / 类名、注册机制 `spring.factories` vs `.imports`、默认值）。

### 17.2 结构约束

- **配对文档两侧同改**：`docs/x.md` ↔ `docs/en/x.md`（`check-docs.py` 会校验配对）。
- **模块树三处同批**：新增 / 同步模块时，`pom.xml` + `.agent/context/module.md` + `docs/modules.md` + `docs/en/modules.md` 一起改。
- **门禁清单**：新增 / 同步门禁时回查 `CONTRIBUTING.md` 的 Static Analysis & Binary Compatibility / Workflow Actions / Test Coverage 三节。
- `CHANGELOG.md` 与 `docs/en/changelog.md` **除版本线归属外无需同步**（共有段落逐节 diff 一致）；`docs/(en/)breaking-changes.md` 要按**本分支**的破坏性变更**重写**，不是照搬 master 条目。

### 17.3 同步落地后必须回查的表述类型（漏了就是「文档过期」）

1. **脚本坐标与默认值**（同步时逐字照搬未适配，如 `SERVLET_JAR` 仍指 jakarta 产物 ⇒ 与本分支 pom 的 javax / 版本矛盾）
2. **门禁清单**（「Not ported」/「do run」两栏）
3. **模块数**（含 `coverage-aggregate`）
4. **对比基线**（Boot / Tomcat / jakarta 版本）
5. **源码基线分支**（把 `master` 当成本分支源码基线，写成「以当前 master 为准」）
